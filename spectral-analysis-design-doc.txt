Executive Summary`n`nThis document defines the technical architecture for the Spectral Analysis feature within the Perceptiv Admin Dashboard. The feature enables vibration analysts to investigate raw waveform data and FFT spectra directly from alarm contexts, supporting root cause analysis of equipment health issues.`n`nThe design prioritizes a clean separation between a data-serving backend API and a client-side visualization layer. FFT computation is performed in the browser, keeping the backend as a reusable data service that can serve both the Perceptiv dashboard and potential third-party consumers.`n`n`n`n`n2. Architectural Decisions`n`nThe following key decisions were made during design and are documented here with rationale for traceability.`n`n`nID`nDecision`nRationale`nADR-001`nFFT computed client-side in the browser`nEliminates API round-trip on axis toggle. Enables backend to remain a pure data service. Browser can compute FFT on 16,384 points in <50ms using optimized JavaScript libraries. Third-party API consumers can perform their own analysis.`nADR-002`nBackend decodes base64 and scales to g values`nRaw sensor data is base64-encoded 16-bit signed integers. Decoding and scaling require knowledge of config.accelRange_g. Centralizing this in the backend ensures consistent data interpretation across all consumers.`nADR-003`nPlotly.js for chart rendering`nProvides zoom, pan, hover tooltips out of the box. Handles 16,384 data points with interactive performance. Supports scientific chart conventions (axis labels, units). Significantly reduces frontend development time compared to D3.js.`nADR-004`nAll three axes loaded in a single API call`nA single waveform payload contains rawHoriz, rawVert, and rawAxial. Loading all three at once avoids repeated API calls when the analyst toggles between axes. Payload size is ~100KB decoded per axis, totaling ~300KB — acceptable for desktop use.`nADR-005`nSample rate read from sensor config metadata`nActual sample rates vary per sensor (e.g., 6547.3 Hz vs 6513.9 Hz). The system must use config.sampleRate_Hz from each payload, not hardcoded nominal values, to ensure accurate frequency axis computation.`n`n`n`n`n3. System Architecture`n`n`n3.1 High-Level Data Flow`n`nThe spectral analysis feature follows a linear data pipeline from sensor hardware through to browser-rendered visualization.`n`n`n`nSR-71VT`n`nSensor`n`nGateway`n`nAzure Cloud`n`n(ADLS)`n`nBackend API`n`n(Node.js)`n`nFrontend`n`n(React)`n`nCollects raw`n`nacceleration at`n`n~6547 Hz for`n`n~2.5 seconds`n`nReceives`n`ntelemetry,`n`nforwards to`n`ncloud`n`nStores raw`n`nwaveform as`n`nbase64-encoded`n`nJSON blobs`n`nReads from ADLS,`n`ndecodes base64,`n`nscales to g values,`n`nreturns JSON arrays`n`nRenders time`n`nwaveform, computes`n`nFFT client-side,`n`nPlotly.js charts`n`n`n`nData transformation at each stage: The sensor captures 16,384 samples (2^14, a power of 2 optimized for FFT) as raw acceleration data. The gateway transmits this as telemetry to Azure, where it is stored in ADLS as a JSON blob containing base64-encoded 16-bit signed integers. The backend API reads this blob, decodes the base64 string, unpacks the 16-bit integers, and scales them using the formula: value_g = raw_int × (accelRange_g / 32768). The frontend receives clean g-value arrays and computes FFT in the browser.`n`n`n`n`n3.2 Backend API Design`n`n`n3.2.1 API Endpoints`nEndpoint`nMethod`nPurpose`nRequirement`n/api/waveform/{sensorId}/{timestamp}`nGET`nReturns decoded waveform data for all three axes at the specified timestamp. enabling side-by-side spectral comparison.`nFR-007`n`n`n`n`n3.2.2 Response Schema – Single Waveform`n`nThe API returns a JSON object containing sensor metadata and decoded acceleration arrays for all received:`n`n`nAuthenticate request using existing JWT token from the Perceptiv session.`n`n`nQuery ADLS for the raw waveform blob matching the sensorId and timestamp.`n`n`nDecode base64 strings (rawHoriz, rawVert, rawAxial) into byte arrays.`n`n`nUnpack as 16-bit signed little-endian integers (Int16LE), yielding 16,384 integer values per axis.`n`n`nScale to g values using: value_g = raw_int × (config.accelRange_g / 32768).`n`n`nCompute derived metadata: duration, Nyquist frequency, and frequency resolution from config.sampleRate_Hz and sample count.`n`n`nReturn JSON response with all three axes and metadata.`n`n`n`n`n3.3 Frontend Architecture`n`n`n3.3.1 Component Hierarchy`nComponent`nResponsibility`nRequirement`nSpectralAnalysisPage`nTop-level page container. The 16,384-sample input (2^14) is ideal for this.`n`nFFT processing steps within the FFTChart component:`n`n`nReceive the time-domain g-values array for the selected axis from parent state.`n`n`nApply a Hanning window to reduce spectral leakage (a common signal processing step that minimizes edge effects in FFT).`n`n`nCompute the FFT, yielding complex output (real and imaginary components).`n`n`nCalculate magnitude spectrum: magnitude = sqrt(real² + imag²) / N, where N is the sample count.`n`n`nGenerate the frequency axis: each bin k corresponds to frequency = k × (sampleRate_Hz / N), from 0 Hz to Nyquist (sampleRate_Hz / 2).`n`n`nRender using Plotly.js with hover tooltip displaying: frequency (Hz), amplitude (g rms), and CPM (frequency × 60).`n`n`n`n`n3.4 Page Layout`n`nThe spectral analysis view follows the layout pattern established by the existing Perceptiv Data Viewer, adapted for the admin dashboard context.`n`n`n`nHEADER BAR: Sensor ID | Timestamp | Sensor Type | Health Status`n`nAXIS SELECTOR: [ Horizontal ] [ Vertical ] [ Axial ]`n`nTIME WAVEFORM CHART`n`nX: Time (seconds, 0 to ~2.5s) | Y: Acceleration (g)`n`nInteractive: Zoom, Pan, Reset, Hover Cursor`n`nFFT SPECTRUM CHART`n`nX: Frequency (Hz, 0 to ~3274 Hz) | Y: Amplitude (g rms)`n`nInteractive: Zoom, Pan, Reset, Hover Cursor with Hz + g rms + CPM`n`n`n`n`n4. Non-Functional Requirements – Architecture Mapping`n`nEach non-functional requirement is addressed by a specific architectural approach.`n`n`nNFR`nRequirement`nArchitectural Approach`nNFR-001`nRender within 5 seconds (click to interactive chart)`nBackend caching of recently accessed blobs. Single API call for all 3 axes. Client-side FFT avoids second round-trip. Plotly.js WebGL renderer for large datasets.`nNFR-002`n50 concurrent analysts without >10% degradation`nStateless backend API. Horizontal scaling via container orchestration. ADLS read operations are inherently parallelizable.`nNFR-003`nChrome, Edge, Firefox (latest 2 versions)`nPlotly.js and fft.js are compatible with all modern browsers. No browser-specific APIs used.`nNFR-004`nExact metadata-based computation (no rounding)`nSample rate passed through API response as-is from source JSON. Frontend FFT uses the exact value for frequency axis generation. No intermediate rounding in the pipeline.`n`n`n`n`n8. Glossary`nTerm`nDefinition`nFFT`nFast Fourier Transform – algorithm that converts a time-domain signal into its frequency components`nNyquist Frequency`nMaximum observable frequency = sample rate ÷ 2. Frequencies above this cannot be detected.`nFrequency Resolution`nSmallest frequency difference distinguishable in the FFT = sample rate ÷ sample count`nRMS`nRoot Mean Square – statistical measure of average signal energy`nCrest Factor`nRatio of peak amplitude to RMS. Indicates impulsiveness of the signal.`nCPM`nCycles Per Minute = frequency in Hz × 60. Common in rotating machinery analysis.`nOrder (1X, 2X)`nMultiples of shaft rotation frequency. 1X = imbalance, 2X = misalignment.`nBPFO / BPFI`nBall Pass Frequency Outer/Inner – bearing defect frequencies calculated from geometry`nADLS`nAzure Data Lake Storage – cloud storage for large binary/JSON data`nHanning Window`nWindowing function applied before FFT to reduce spectral leakage at signal edges`nSpectral Leakage`nArtifact in FFT caused by non-periodic signal edges, spreading energy across bins`nBase64`nEncoding scheme that represents binary data as ASCII text for safe transmission in JSON`n`n`n
